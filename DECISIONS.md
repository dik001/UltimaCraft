# Архитектурные решения

## ADR-001 — Реляционная модель рецептов

**Статус:** принято.  
**Решение:** рецепт — отдельный агрегат; `Recipe.result_item_id` не уникален, поэтому один предмет имеет несколько рецептов. Ингредиенты — строки с обязательным FK на `Item`.  
**Причина:** это необходимо для рекурсивных цепочек и альтернативных способов производства.

## ADR-002 — Несколько способов получения

**Статус:** принято.  
**Решение:** справочник `AcquisitionMethod` и связующая сущность `ItemAcquisition`, а не поле на Item. Системные коды: `FIND`, `TRADER`, `AUCTION`, `CRAFT`.  
**Причина:** способы независимы и могут действовать одновременно.

## ADR-003 — Цены и точные числа

**Статус:** принято.  
**Решение:** цены хранятся в `ItemPrice`, уникальны по `(item_id, price_type)`. Деньги и измеримые значения используют `Numeric(18,4)`/`Decimal`, а не float.  
**Причина:** цена скупщика и рынок обновляются независимо; decimal предотвращает двоичные ошибки и допускает дроби.

## ADR-004 — Вычисляемое участие в рецептах

**Статус:** принято.  
**Решение:** «используется в крафтах» вычисляется через `EXISTS RecipeIngredient`; cached boolean не создаётся.  
**Причина:** исключается рассинхронизация.

## ADR-005 — Удаление и владение

**Статус:** принято.  
**Решение:** внешние ссылки ограничивают удаление. Каскад разрешён только для собственных строк явно удаляемого агрегата после подтверждения. Сервис до операции возвращает человекочитаемое описание зависимостей.  
**Причина:** защита большой вручную созданной базы важнее удобства каскадного удаления.

## ADR-006 — Alembic обязателен

**Статус:** принято.  
**Решение:** схема создаётся и обновляется ревизиями Alembic, а `create_all` разрешён только изолированным unit-тестам.  
**Причина:** база живёт долго, поэтому эволюция схемы должна быть воспроизводимой.

## ADR-007 — Локальные изображения

**Статус:** принято.  
**Решение:** исходный файл копируется под UUID с допустимым расширением в `data/images/items`; БД хранит POSIX-подобный относительный путь. Отсутствие файла не является фатальной ошибкой.  
**Причина:** небольшая SQLite БД, переносимость каталога данных и безопасный preview.

## ADR-008 — Режимы и пароль

**Статус:** принято.  
**Решение:** Viewer — режим запуска по умолчанию. Локальная настройка администратора хранит salted PBKDF2 hash в `data/settings.json`; игровой БД это не касается. UI и сервисный guard блокируют игровые изменения, быстрый upsert аукционной цены разрешён пользователю.  
**Причина:** достаточно локальной защиты без ложной сложности аккаунтов.

## ADR-009 — Сохранение агрегата предмета

**Статус:** принято.  
**Решение:** карточка предмета с рецептами сохраняется атомарно одной транзакцией; агрессивного autosave нет.  
**Причина:** отмена изменений должна быть настоящей, частичные рецепты недопустимы.

## ADR-010 — Экспорт/импорт JSON

**Статус:** отложено до завершения обязательных сценариев.  
**Решение:** сервисный слой и стабильные коды подготовлены, но SQLite остаётся каноническим форматом.  
**Причина:** импорт не должен снижать качество основных редакторов и защиты данных.

## ADR-011 — Unicode-нормализация имён справочников

**Статус:** принято после теста этапа 2.  
**Проблема:** SQLite `NOCASE` регистронезависим только для ASCII; проверка показала, что кириллические «Материалы» и «материалы» проходят обычное UNIQUE как разные значения.  
**Проверка совместимости:** перед изменением пользовательские справочники в рабочей БД пусты; присутствуют только 4 системных способа получения. Для существующих и будущих БД используется отдельная миграция с заполнением ключей.  
**Решение:** у именованных справочников хранится технический `name_key = NFKC(name.strip()).casefold()`, защищённый уникальным индексом (для подгруппы — вместе с `group_id`). Поле не показывается в UI.  
**Причина:** уникальность русских имён должна обеспечиваться самой БД, а не зависеть только от UI.

## ADR-012 — Восстановление номера начальной ревизии

**Статус:** принято после миграционного теста этапа 2.  
**Проблема:** ранняя версия `alembic/env.py` выполняла `PRAGMA` в неявной транзакции; SQLite сохранял DDL, но мог откатить строку `alembic_version`.  
**Проверка совместимости:** восстановление срабатывает только если таблица версий пуста и присутствует полный точный набор таблиц начальной схемы; частичная/чужая схема блокируется.  
**Решение:** транзакция после `PRAGMA` явно завершается, а startup один раз штампует начальную ревизию только для проверенной полной схемы.  
**Причина:** сохранить уже введённые данные и сделать обновление воспроизводимым без пересоздания файла.

## ADR-013 — Нормализованный поисковый ключ предмета

**Статус:** принято перед этапом 5.  
**Проблема:** SQLite `lower()`/`NOCASE` не обеспечивают корректный регистронезависимый поиск кириллицы, а фильтрация тысяч строк в Python ухудшает отзывчивость.  
**Проверка совместимости:** рабочая БД находится на `a14c8b31e2f0` и пока содержит 0 предметов; миграция всё равно заполняет ключи для совместимости с другими копиями.  
**Решение:** добавить индексированное техническое поле `item.name_key = NFKC(name.strip()).casefold()` и поддерживать его ORM-событиями. Поиск также использует уже существующие `name_key` групп/подгрупп.  
**Причина:** поиск русских названий выполняется одним индексируемым SQL-запросом и не блокирует UI загрузкой всех полных карточек.

## ADR-014 — Функциональная палитра «закат»

**Статус:** принято по визуальному референсу пользователя после версии 0.1.0.  
**Решение:** ночной синий используется как нейтральная основа, бирюзовый — для навигации и выбранных элементов, жёлтый — для основных действий, оранжевый — для hover/pressed, розовый — для опасных действий. Светлый текст сохраняет контраст на тёмных поверхностях.  
**Причина:** перенести настроение референса на собственный интерфейс, сохранив визуальную иерархию и читаемость больших форм.

## ADR-015 — Dashboard-композиция и прозрачные подписи

**Статус:** принято по второму визуальному референсу пользователя.  
**Решение:** главное окно разделено на постоянный брендированный сайдбар и рабочую область с верхней строкой, фильтрами и карточками. Тяжёлые контуры заменены скруглёнными поверхностями с небольшим перепадом тона. Все `QLabel`, включая подписи `QFormLayout`, имеют прозрачный фон; горизонтальная прокрутка карточки запрещена.  
**Причина:** приблизить визуальную иерархию к современному аналитическому dashboard и убрать нежелательные прямоугольные подложки под текстом.

## ADR-016 — Нормализация сигналов изменения UI

**Статус:** принято после воспроизведения аварии редактора.  
**Проблема:** `valueChanged`, `currentIndexChanged`, `textChanged` и `toggled` передавали значение напрямую в пользовательский `Signal()` без аргументов, что вызывало `TypeError` при редактировании энергии, количеств, эффектов и других полей.  
**Проверка совместимости:** ошибка находится только в слое PySide6; схема и содержимое SQLite корректны (`integrity_check = ok`), миграция не требуется.  
**Решение:** все разнотипные Qt-сигналы проходят через принимающий `*_args` адаптер и далее испускают единый безаргументный сигнал изменения формы. Глобальный фон снят с `QWidget`; пассивные подписи и чекбоксы прозрачны.  
**Причина:** форма использует событие только как признак несохранённых изменений и не должна зависеть от сигнатуры конкретного Qt-контрола.

## ADR-017 — Изоляция логирования приложения от Alembic

**Статус:** принято после диагностики пустого `logs/app.log`.  
**Проблема:** `logging.config.fileConfig` внутри программной миграции Alembic заменял root handlers и отключал уже созданные именованные логгеры; аварийный обработчик показывал диалог, но traceback не попадал в файл.  
**Проверка совместимости:** изменение не касается ревизий или структуры БД; `alembic check` не обнаруживает новых операций.  
**Решение:** программная миграция передаёт Alembic флаг запрета перенастройки logging, а CLI сохраняет штатный консольный режим. Файловый handler приложения определяется по точному абсолютному пути, аварийные записи принудительно flush-ятся.  
**Причина:** миграционный инструмент внутри desktop-процесса не должен разрушать диагностику приложения.

## ADR-018 — Вставка изображения из clipboard через временный файл

**Статус:** принято по запросу пользователя.  
**Решение:** UI кодирует изображение из системного буфера во временный PNG с автоматическим удалением и передаёт его в существующий path-based `ImageService`. Постоянный файл создаётся только при `Сохранить`; отмена, замена и переключение карточки удаляют временный файл. `Ctrl+V` имеет область действия только на preview изображения.  
**Совместимость:** схема БД и формат `image_path` не меняются; миграция не требуется.  
**Причина:** сохранить единый проверенный поток импорта изображений, настоящее отложенное сохранение формы и обычную вставку текста в редакторах.

## ADR-019 — Атомарное быстрое создание ингредиентов

**Статус:** принято после уточнения сценария массового наполнения пользователем.  
**Проблема:** редактируемый `IdComboBox` позволял напечатать отсутствующее имя, но сохранял прежний скрытый `item_id`. В результате текст `Порох` мог визуально отображаться перед сохранением, а рецепт записывал ID первого предмета списка.  
**Проверка совместимости:** схема БД не меняется; новый ресурс всё равно становится полноценной строкой `Item`, а `RecipeIngredient.item_id` остаётся обязательным FK. Рабочая БД цела, но текущий рецепт уже содержит разрешённую пользователем самоссылку.  
**Решение:** точное имя существующего предмета автоматически разрешается в его ID. Для отсутствующих имён перед сохранением показывается один компактный диалог группы/подгруппы; новые минимальные `Item` и весь агрегат рецепта записываются одной транзакцией. Неизвестный текст никогда не использует прежний ID. Прямая самоссылка результата в ингредиентах разрешена; будущий Craft Engine обязан обнаруживать циклы при обходе графа.  
**Причина:** обеспечить быстрый ввод новых ресурсов без свободнотекстовых ингредиентов, ложных связей и частично созданных данных.

## ADR-020 — Ручной ввод группы и подгруппы при быстром создании ресурса

**Статус:** принято по уточнению сценария массового наполнения пользователем.  
**Проблема:** диалог быстрого создания ингредиента позволял ввести название нового предмета, но группу и подгруппу можно было только выбрать из заранее заполненных справочников. Это заставляло прерывать ввод рецепта и отдельно открывать редактор справочников.  
**Проверка совместимости:** схема SQLite уже содержит отдельные `ItemGroup` и `ItemSubgroup`, нормализованные ключи и внешние ключи; миграция не требуется. Существующие строки и изображения не преобразуются.  
**Решение:** поля группы и подгруппы в диалоге становятся редактируемыми. Точное безрегистровое совпадение использует существующую запись, отсутствующее имя создаёт новую группу или подгруппу. Новые справочники, минимальные предметы-ресурсы и рецепты сохраняются одной транзакцией; ошибка откатывает весь набор. Подгруппа всегда связывается с выбранной или одновременно создаваемой группой.  
**Причина:** сохранить реляционную целостность и одновременно убрать лишние переходы при массовом вводе базы.

## ADR-021 — Обновление справочников в открытом черновике карточки

**Статус:** принято после воспроизведения ошибки сохранения существующего навыка.  
**Проблема:** строки рецепта получали снимок вариантов при создании виджета. Справочник мог уже содержать новый навык, но открытая карточка продолжала проверять текст по старому списку и сообщала, что значение отсутствует.  
**Проверка совместимости:** данные и внешние ключи SQLite корректны, изменение относится только к синхронизации UI; миграция не требуется.  
**Решение:** после закрытия менеджера справочников все открытые комбобоксы обновляют варианты из БД. Выбранный ID сохраняется, а введённый текст сопоставляется с новым справочником через `NFKC + casefold`. Строки рецепта, количества и признак несохранённых изменений не пересоздаются.  
**Причина:** изменения справочников должны становиться доступными в текущем черновике сразу и без потери ручного ввода.
